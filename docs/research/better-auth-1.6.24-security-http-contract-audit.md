# Better Auth 1.6.24 security and HTTP contract audit

Source ticket: [Audit Better Auth 1.6.24 security and HTTP contract deltas](https://github.com/salasebas/rustauth/issues/214)

## Answer

Better Auth v1.6.24 is not a wire-compatible patch over v1.6.9 for
RustAuth's declared server parity surface. The interval adds one opt-in HTTP
route, adds methods and well-known aliases, changes request and response
schemas, changes status/error/redirect contracts, changes cookie and cache
headers, makes many formerly best-effort security checks fail closed, and adds
atomicity requirements to single-use authentication state.

The highest-risk parity work is not the additive route surface. It is the
change in authority: v1.6.24 repeatedly stops trusting cookie-cache snapshots,
caller-supplied OAuth/SSO identity, unverified local email, unscoped provider
identifiers, non-atomic verification rows, unvalidated origins/redirects, and
untrusted proxy headers.

This is an **upstream-only delta audit**. It does not assert that RustAuth has
any corresponding defect. No concrete RustAuth vulnerability was established,
so this report is suitable for the public issue workflow. Implementation-level
reconciliation of a security-sensitive row should first determine privately
whether RustAuth is already stricter before publishing any exploitable detail.

## Audit basis

- Baseline: Better Auth [`v1.6.9`](https://github.com/better-auth/better-auth/commit/f484269228b7eb8df0e2325e7d264bb8d7796311).
- Target: Better Auth [`v1.6.24`](https://github.com/better-auth/better-auth/commit/9a661c7b7abceaa81123b2c56757ee24f3ad2ed6).
- Full official comparison: [`v1.6.9...v1.6.24`](https://github.com/better-auth/better-auth/compare/v1.6.9...v1.6.24).
- Scale: 380 commits and 742 changed files overall. The mapped server-package
  pass covered 208 commits and 365 changed files across `better-auth`,
  `@better-auth/core`, `@better-auth/oauth-provider`, `@better-auth/sso`,
  `@better-auth/scim`, `@better-auth/passkey`, `@better-auth/api-key`, and
  `@better-auth/stripe`.
- Evidence: tagged source, tagged tests, per-package changelogs, commit diffs,
  and the official [June 2026 security update](https://github.com/better-auth/better-auth/blob/v1.6.24/docs/content/blogs/security-update-june-2026.mdx).
- Release-note reconciliation: every commit touching the audited package
  sources was checked against every `packages/*/CHANGELOG.md`. The audit also
  inspected commits with no changelog reference.

Client-only state management, framework UI behavior, CLI-only generation, and
adapter-only migration mechanics are outside this ticket except where they
change an observable auth response or are required by a security boundary.
Those areas remain part of the wider parity map.

## Reading the matrices

Flags:

- **A** — additive.
- **B** — breaking or compatibility-sensitive.
- **S** — security-sensitive.
- **FC** — a formerly permissive or ambiguous path now fails closed.
- **AT** — concurrency/atomicity contract.
- **RN-** — behavioral or boundary change absent from package release notes.

“Breaking” does not mean “undesirable.” Most breaking rows are deliberate
security corrections: a request accepted by v1.6.9 is rejected or redirected
differently by v1.6.24.

Commit links are primary evidence: they show the exact official source and the
regression tests introduced with it. Tagged test links are added for broad
multi-file changes.

## 6. Route and method delta summary

The route scan found these net additions or method/header-level changes on the
mapped server surface:

1. Opt-in new `GET /oauth-popup/start`; a popup-marked provider callback can
   return 200 HTML with CSP/no-store instead of the normal 302.
2. `POST /oauth2/userinfo` is accepted in `@better-auth/oauth-provider` in
   addition to GET.
3. Path-prefixed OAuth issuers gain direct OAuth authorization-server and OIDC
   well-known aliases, GET/HEAD only.
4. `GET /get-session` adds `Cache-Control: no-store`.
5. Root-mounted paths that do not begin with `basePath` now return 404.
6. Several functions are explicitly marked server-only. They remain available
   through trusted `auth.api.*` calls and absent from the HTTP router/OpenAPI.
   This is a source-level security boundary, not a net route removal: the
   path-less v1.6.9 functions already returned 404 over HTTP.

No other mapped route path was added or removed. Most of the interval's HTTP
delta is validation, authority, response/error shape, redirect destination,
header, or concurrency behavior on existing routes.

## 7. Fail-open compatibility knobs that remain at v1.6.24

The target is substantially stricter but is not uniformly fail closed:

- `account.accountLinking.requireLocalEmailVerified:false` restores legacy
  implicit linking and is deprecated.
- Organization invitation recipient endpoints can retain unverified-email
  behavior through `requireEmailVerificationOnInvitation:false`; when unset,
  v1.6.24 also preserves the opaque emailed-invitation flow.
- `remoteVerify.allowMissingAudience:true` permits an introspection response
  with no audience while still rejecting a mismatching audience.
- `allowPlainCodeChallengeMethod:true` preserves plain PKCE and the missing
  method fallback in legacy OIDC/MCP plugins.
- Custom rate-limit storage without atomic `consume` retains best-effort
  concurrency behavior and warns.
- Secondary verification storage without `getAndDelete` uses an in-process
  lock that cannot guarantee cross-process single use and warns.
- API-key quota/rate counters in secondary-storage-only deployments remain
  best effort without database fallback.
- `providerOwnership.enabled:false` remains the SCIM patch-line compatibility
  default described by the v1.6.11 release.
- Trusted origins are intentional escape hatches for internal SSO IdP
  endpoints; operator configuration becomes part of the SSRF boundary.

Each retained knob requires an explicit RustAuth disposition. Silent adoption
of a fail-open compatibility mode would conflict with the repository's
fail-closed security rule.

## 8. Changes absent from release notes

Two observable changes and one security-boundary clarification were absent from
all package changelogs:

1. [Atomic SAML AuthnRequest consumption](https://github.com/better-auth/better-auth/commit/a6b0295df3d6ced4beb460ef8082ff941facae2f)
   changes concurrent ACS behavior so one request succeeds and a racer is
   rejected.
2. [OpenAPI model ID/returned-field requiredness](https://github.com/better-auth/better-auth/commit/3310ebc4a0c99d10c7fa13fef269db549a479dcd)
   changes generated schemas.
3. [Explicit server-only endpoint metadata](https://github.com/better-auth/better-auth/commit/7faddd4a1d15a7d82c0c8ece7ad65c4a4955d4b6)
   makes a critical boundary structural and corrects misleading endpoint
   comments, but does **not** change current HTTP reachability because those
   endpoints were already path-less.

Other unnoted audited commits were net-zero, type-only, test-only, equivalent
refactors, or superseded before v1.6.24. In particular, headerless
`get-session` support was added and then reverted, so it creates no tag-to-tag
contract delta. Centralizing the request-IP resolver and spelling cookie regex
ranges explicitly preserve behavior.

## 9. Required parity follow-up

This audit resolves the upstream inventory, not RustAuth dispositions. The
wider parity map should turn the rows above into execution decisions grouped by
owner:

- core router/origin/session/cookie/rate-limit behavior;
- verification storage and adapter atomic primitives;
- plugin routes and security options;
- OAuth provider and social-provider validation;
- SSO/SAML/SCIM behavior;
- passkey and Stripe behavior;
- OpenAPI and public error/response contracts;
- migrations required by two-factor lockout and any defense-in-depth unique
