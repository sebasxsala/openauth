# RustAuth v1.6.9 declared parity surface and historical divergences

- Status: research baseline
- Snapshot: RustAuth commit `23130f43b82ee1c1c3d7d366132f6ec75a58390e`
- Upstream pin: Better Auth `1.6.9`, commit `f484269`
- Ticket: [Inventory RustAuth declared parity surface and historical divergences](https://github.com/salasebas/rustauth/issues/212)
- Map: [Wayfinder: Better Auth 1.6.24 observable parity](https://github.com/salasebas/rustauth/issues/210)

## Executive summary

At the v1.6.9 pin, RustAuth declares a server/runtime parity surface spread across 23
published crates. The workspace also contains one unpublished integration-test crate
and one unpublished Stripe smoke-server example. The public surface is not one API:
it comprises the facade and builder, the core HTTP contract, plugin route and schema
contributions, protocol-specific sibling crates, framework adapters, database and
secondary-storage adapters, and the CLI. Browser/client packages and framework
middleware outside the two Rust adapters are not represented.

The local implementation is generally broader and fresher than its parity prose.
Every published crate has a README and `UPSTREAM.md`, but those files are not a
reliable machine-readable manifest:

- several test-count and release/version claims are stale;
- the facade README contradicts current feature re-exports and plugin constructor
  signatures;
- the facade `UPSTREAM.md` advertises a public migration method that is intentionally
  not public;
- the SSO documentation understates when signed SAML support is enabled;
- the Fred parity evidence refers to a test file and example usage that are absent;
- the Diesel parity file does not use the same explicit
  difference/gap/test-evidence structure as the other adapter reports; and
- parity-index prompt links and several smoke-test links are broken.

The baseline therefore needs three different labels:

1. **User-visible contract** — HTTP method/path, payload/error behavior, cookie and
   session behavior, defaults, persistent schema, migrations, CLI output and safety
   behavior.
2. **Rust-public contract** — exported types, traits, builders, features, adapter and
   callback interfaces. These matter to Rust integrators even when they are not
   Better Auth JavaScript contracts.
3. **Internal implementation choice** — crate boundaries, Tokio task-local state,
   WebAuthn/SQL/SAML libraries, cache representation, and typed internal models.
   These are not parity differences unless they change observable behavior.

The currently documented observable exceptions are concentrated in intentional
security hardening, Rust-specific API shape, unsupported upstream platforms, and a
small set of acknowledged gaps. The clearest current observable gaps are the OAuth
provider client-update method (`POST` instead of upstream `PATCH`), Actix response
metadata that is not preserved, absent SQLite support in Diesel, non-portable legacy
Redis/Fred data, and CLI omissions that are explicitly outside its current Rust
configuration model. These exceptions must be re-evaluated rather than grandfathered
when the v1.6.24 map decides target dispositions.

## Scope and method

This is an inventory of RustAuth's declared and locally observable v1.6.9 baseline,
not a fresh comparison against a downloaded Better Auth source tree. The pinned
upstream checkout is not present under `reference/upstream-src/`; the repository's
checked-in parity reports are therefore the source for historical upstream claims.
The inventory cross-checks those claims against:

- the workspace and crate manifests;
- public exports and option/builders;
- route registration code;
- logical and physical schema declarations;
- database, secondary-storage, and rate-limit traits;
- checked-in tests and examples;
- every published crate README and `UPSTREAM.md`;
- the parity index, changelog, root README, and release guide.

Static test counts below count `#[test]` and `#[tokio::test]` attributes. They are
freshness indicators, not semantic parity scores. No test was treated as proof of
upstream equivalence solely because it exists.

## Boundary of the declared parity surface

### Included

- `rustauth`: compatibility facade, builder, HTTP handler, prelude, and feature-gated
  re-exports.
- `rustauth-core`: authentication options, routes, schemas, plugin host, session and
  cookie behavior, storage contracts, rate limiting, errors, hooks, and outbound work.
- `rustauth-plugins`: the general Better Auth plugin catalog implemented in Rust.
- Protocol and commercial siblings: OAuth helpers, OAuth provider, social providers,
  OIDC helpers, SSO, SAML, SCIM, passkeys, Stripe, i18n, and telemetry.
- Runtime adapters: Axum and Actix Web.
- Persistence adapters: SQLx, Diesel, Tokio PostgreSQL, Deadpool PostgreSQL, Redis,
  and Fred.
- `rustauth-cli`.
- `rustauth-integration-tests` and `rustauth-example-stripe-smoke` as non-published
  validation infrastructure.

### Excluded or not independently implemented

- Better Auth browser/client packages, client-side plugins, React/Vue/Svelte clients,
  and browser test matrices.
- JavaScript framework middleware other than the observable behavior implemented by
  the Axum and Actix adapters.
- Node/Bun/D1/MongoDB/MSSQL adapter surfaces.
- Better Auth's TypeScript `auth.api` in-process caller. RustAuth exposes an HTTP
  handler and typed Rust extension APIs instead.
- TypeScript configuration execution and ORM code generation. The CLI operates on
  static `rustauth.toml` and SQL migrations.

## Core server contract

### Public options and extension contracts

[`RustAuthOptions`](../../crates/rustauth-core/src/options.rs) exposes these option
families:

- application name, base URL/path, secrets, trusted origins, and disabled paths;
- session, user, account, verification, email/password, email verification, password,
  change-email, and delete-user behavior;
- database and lifecycle hooks, API error behavior, logger, advanced cookie/proxy
  settings, and rate limits;
- secondary storage and plugin registration;
- social providers, telemetry, runtime mode, and experimental switches.

The public plugin host supports endpoints, sync and async middleware, hooks, schema
contributions, per-path rate rules, error definitions, database hooks and migrations,
social providers, password validators, and plugin state.

The principal storage contracts are:

- [`DbAdapter`](../../crates/rustauth-core/src/db/adapter.rs): adapter identity and
  capabilities; create/find/count/update/delete operations; bulk operations;
  transactions; schema creation; migrations; and plugin migrations.
- [`SecondaryStorage`](../../crates/rustauth-core/src/options/storage.rs):
  `get`, `set`, `set_if_not_exists`, `delete`, `take`,
  compare-and-set, and delete-if-value. A zero TTL deletes. Atomic operations are
  required for cross-process correctness where the caller relies on them.
- `RateLimitStore`: atomic consume semantics. The legacy synchronous
  `RateLimitStorage` contract cannot guarantee cross-process atomicity.
- Outbound email/SMS hooks return an `OutboundSendFuture` and are dispatched after the
  success response rather than awaited in the request path.

Missing client IPs fail closed by default for rate limiting.

### Core HTTP routes

With OAuth/social support enabled, core registers 33 method/path entries over 30
unique paths. `GET` and `POST` variants account for the duplicates.

| Area | Registered method/path contract |
|---|---|
| Health | `GET /ok` |
| Sign-up/sign-in | `POST /sign-up/email`, `POST /sign-in/email`, `POST /sign-in/social` |
| OAuth callbacks/linking | `GET|POST /callback/:id`, `POST /link-social`, `GET /error` |
| Sessions | `GET|POST /get-session`, `GET /list-sessions`, `POST /update-session`, `POST /revoke-session`, `POST /revoke-sessions`, `POST /revoke-other-sessions`, `POST /sign-out` |
| Accounts/tokens | `GET /list-accounts`, `POST /unlink-account`, `POST /get-access-token`, `POST /refresh-token`, `GET /account-info` |
| User/email | `POST /update-user`, `POST /change-email`, `POST /send-verification-email`, `GET /verify-email`, `POST /delete-user`, `GET /delete-user/callback` |
| Password | `POST /change-password`, `POST /set-password`, `POST /verify-password`, `POST /request-password-reset`, `GET /reset-password/:token`, `POST /reset-password` |

`GET /ok` intentionally returns plain `OK`; the checked-in parity report records
Better Auth's response as JSON.

### Core logical schema

| Logical model | Default physical table | Conditional behavior |
|---|---|---|
| `user` | `users` | always present |
| `session` | `sessions` | omitted when sessions live only in secondary storage |
| `account` | `accounts` | always present |
| `verification` | `verifications` | omitted when verifications live only in secondary storage |
| `rate_limit` | `rate_limits` | present only for database-backed rate limiting |

All models support configured table and field mappings. Additional fields, generated
fields, and hidden metadata flow through the shared schema. SQL adapters enforce
strict ASCII identifier validation.

### Recorded core divergences

| Classification | Current RustAuth behavior |
|---|---|
| Intentional Rust API | typed static/dynamic trusted-provider callbacks; typed JSON/redirect errors; JSON Schema/OpenAPI instead of Zod; Tokio task-local request context instead of `AsyncLocalStorage`; no TypeScript-style `auth.api` caller |
| Observable exception | `GET /ok` returns plain text rather than JSON |
| Security hardening | implicit account linking requires verified email or a trusted provider; malformed/untrusted inputs fail closed; production secret checks; SQL identifier validation; escaped `LIKE` wildcards; chunked-cookie constraints |
| Historical gap status | the core `UPSTREAM.md` marks its previously tracked G1–G15 gaps closed |

Recorded plugin-level differences and risks:

- environment variables use the RustAuth prefix;
- One Tap returns a missing-email error with HTTP 400 where the parity report records
  an upstream HTTP 200 error response;
- callback/configuration APIs are typed Rust callbacks and cannot serialize arbitrary
  JavaScript callbacks;
- OAuth proxy payloads are encrypted in RustAuth;
- generic OAuth enforces SSRF controls and accepts only verified ID-token identities;
- API keys can require revalidation and use atomic storage operations;
- OIDC-provider and MCP capabilities moved to the OAuth-provider sibling crate;
- lower-density areas remain the organization edge-case matrix and plugins whose
  correctness depends on an integrator providing truly atomic secondary storage.

## Protocol and service sibling inventory

### OAuth helpers (`rustauth-oauth`)

Public surface: authorization URL building, PKCE/state helpers, token exchange,
userinfo and ID-token verification, JWKS cache, and provider abstractions. It owns no
routes or persistent schema.

Intentional differences include typed Rust callbacks, ignoring protected extension
parameters, rejecting HMAC ID-token algorithms by default, RFC form encoding and
Base64 Basic authentication, a bounded URL-keyed in-process JWKS cache, and an async
provider trait. The caller owns HTTP transport and SSRF policy. The remaining
evidence risk is the lack of a live-provider matrix.

### OAuth provider (`rustauth-oauth-provider`)

Base registration is 26 method/path entries over 25 unique paths, with both `GET` and
`POST` for `/oauth2/continue`:

- discovery: `/.well-known/oauth-authorization-server`,
  `/.well-known/openid-configuration`;
- protocol: `/oauth2/authorize`, `/oauth2/consent`,
  `/oauth2/continue`, `/oauth2/token`, `/oauth2/introspect`,
  `/oauth2/revoke`, `/oauth2/userinfo`, `/oauth2/end-session`,
  `/oauth2/register`;
- client management:
  `/admin/oauth2/create-client`, `/oauth2/create-client`,
  `/oauth2/get-client`, `/oauth2/public-client`,
  `/oauth2/public-client-prelogin`, `/oauth2/get-clients`,
  `/admin/oauth2/update-client`, `/oauth2/update-client`,
  `/oauth2/client/rotate-secret`, `/oauth2/delete-client`;
- stored consent: `/oauth2/get-consent`, `/oauth2/get-consents`,
  `/oauth2/update-consent`, `/oauth2/delete-consent`.

MCP configuration can add `/.well-known/oauth-protected-resource`. JWKS is owned by
the JWT plugin.

Persistent tables are `oauth_clients`, `oauth_refresh_tokens`,
`oauth_access_tokens`, and `oauth_consents`.

Observable and intentional differences:

- client update is currently `POST`; the parity report records upstream `PATCH`;
- physical tables use plural snake-case names;
- stored tokens are hashed, and encrypted token input is rejected;
- continuation accepts both `GET` and `POST`;
- errors are typed; host enforcement remains the plugin host's responsibility;
- no pushed-authorization-request endpoint is exposed.

Open evidence risks are feature/init hook coverage, malformed/runtime permutations,
in-process trusted-client caches, migration prerequisites, MCP host enforcement, and
the client-guard matrix.

### Social providers (`rustauth-social-providers`)

The provider catalog contains all 35 providers claimed by the v1.6.9 parity report
and preserves their declared order. Ten providers have typed callback-specific
customization; the rest use the shared provider contract. Facebook opaque-token and
Twitch JWKS handling are stricter than the recorded upstream behavior. The principal
evidence gap is no live-provider smoke matrix.

### OIDC helpers (`rustauth-oidc`)

Public surface covers discovery, client authentication, token exchange, logout,
introspection, revocation, and metadata. The caller owns HTTP transport and origin
policy. RustAuth persists additional revocation, end-session, and introspection
metadata, redacts client secrets, uses explicit scopes, and keeps helpers separate
from SSO configuration. No open in-scope route/schema gap is declared; SSRF policy is
an operational integration requirement.

### SSO and SAML (`rustauth-sso`, `rustauth-saml`)

SSO registers six default routes, two additional OIDC routes, seven SAML
method/path registrations, and two optional domain-verification routes. With all
protocol features and domain verification enabled, that is 17 registrations over 16
unique paths:

- default: `/sso/register`, `/sign-in/sso`, `/sso/providers`,
  `/sso/get-provider`, `/sso/update-provider`, `/sso/delete-provider`;
- OIDC: `/sso/callback/:providerId`, `/sso/callback`;
- SAML: `/sso/saml2/sp/metadata`, `/sso/saml2/callback/:providerId`,
  `/sso/saml2/sp/acs/:providerId`, `GET|POST /sso/saml2/sp/slo/:providerId`,
  `/sso/saml2/logout/:providerId`;
- domain verification: `/sso/request-domain-verification`,
  `/sso/verify-domain`.

SSO persists `sso_providers`. It redacts secrets, delegates organization provisioning
through the actual organization plugin, uses caller-owned HTTP, and exposes typed
errors. The SAML crate uses `opensaml`; it requires signed assertions by default,
rejects cryptographic operations when the relevant feature is unavailable, exposes
an explicit ACS URL, and warns on deprecated algorithms.

Known evidence and documentation risks:

- no checked-in live-IdP smoke guide despite README/`UPSTREAM.md` links to one;
- application-configured metadata fetches depend on the caller's SSRF policy;
- the direct `rustauth-saml` crate can be built without signed-XML support and then
  fails closed, but `rustauth-sso`'s `saml` feature currently enables the
  `rustauth-saml/saml-signed` feature. SSO prose that describes SAML as unsigned
  unless `saml-signed` is separately enabled is stale;
- no browser client is in scope.

### SCIM (`rustauth-scim`)

SCIM registers 26 method/path entries:

- provider management: `POST /scim/generate-token`,
  `GET /scim/list-provider-connections`,
  `GET /scim/get-provider-connection`,
  `POST /scim/delete-provider-connection`;
- users: `POST|GET /scim/v2/Users`,
  `GET|PUT|PATCH|DELETE /scim/v2/Users/:userId`,
  `POST /scim/v2/Users/.search`;
- groups: `POST|GET /scim/v2/Groups`,
  `GET|PUT|PATCH|DELETE /scim/v2/Groups/:groupId`,
  `POST /scim/v2/Groups/.search`;
- common protocol: `POST /scim/v2/.search`, `POST /scim/v2/Bulk`,
  `GET /scim/v2/Me`, `GET /scim/v2/ServiceProviderConfig`,
  `GET /scim/v2/Schemas`, `GET /scim/v2/Schemas/:schemaId`,
  `GET /scim/v2/ResourceTypes`,
  `GET /scim/v2/ResourceTypes/:resourceTypeId`.

It implements filtering, sorting, projection, pagination, weak ETags, group/profile
storage, and audit metadata.

Persistent tables are `scim_providers`, `scim_user_profiles`, and
`scim_group_profiles`.

Intentional behavior includes hashed provider tokens, ownership requirements for
global providers, rotation only after the hook succeeds, email-shaped usernames,
provisioned `email_verified = true`, delete-as-unlink instead of global user deletion,
fail-closed empty role lists, and organization provisioning through the organization
plugin. `GET Me` is explicitly unimplemented and returns 501. Atomic bulk requires a
transaction-capable adapter. MongoDB is not supported.

### Passkeys (`rustauth-passkey`)

The seven routes are `/passkey/generate-register-options`,
`/passkey/verify-registration`, `/passkey/generate-authenticate-options`,
`/passkey/verify-authentication`, `/passkey/list-user-passkeys`,
`/passkey/update-passkey`, and `/passkey/delete-passkey`. The logical `passkey` model
maps to physical `passkeys`, with hidden WebAuthn credential data.

RustAuth uses `webauthn-rs`, atomically consumes challenges, returns a generic
authentication failure for unknown credentials, requires a fresh session to update
or delete credentials, and applies additional rate limits. Reverse-proxy/RP-ID
configuration, shared challenge storage, and invalid legacy key material remain
operational risks.

### Stripe (`rustauth-stripe`)

The seven routes are `/subscription/upgrade`, `/subscription/list`,
`/subscription/success`, `/subscription/billing-portal`, `/subscription/cancel`,
`/subscription/restore`, and `/stripe/webhook`. Schema contributions are user
`stripe_customer_id`, optional organization customer metadata, `subscriptions`, and
`stripe_webhook_events`.

The client is injectable. Webhook idempotency is durable and retryable, redirect URLs
are explicitly validated, metadata spoofing is rejected, and the response includes a
RustAuth `group` extension. No plugin-specific rate-limit rules are declared.
Migration setup, best-effort customer synchronization, list pagination limits, and a
live Stripe smoke test remain operational/evidence risks; the README's linked smoke
assets are absent.

### i18n (`rustauth-i18n`)

i18n owns no route or schema. It provides typed translation keys, locale resolution,
sync and async callbacks, session hydration, and response mutation.

Differences include explicit configuration errors, case-insensitive locale matching,
exact-region-before-base matching, a broader JSON error-code gate, and split sync vs
async hooks. Missing translations intentionally fail open. The synchronous handler
cannot hydrate locale from database state, and localization is JSON-response-only.

### Telemetry (`rustauth-telemetry`)

Telemetry owns no auth route or schema. It provides opt-in event collection,
environment/runtime detection, a deployer endpoint, configurable sinks, redaction,
and test-injectable collectors. `RUSTAUTH_*` configuration is used; explicit false is
a hard opt-out. CPU model/speed/memory fields can be null. There is no default
maintainer collector. Collector deployment is outside the server parity surface.

### CLI (`rustauth-cli`)

Commands are:

- `init`, `doctor`, `info`, `secret`;
- `db status`, `db generate`, `db migrate`;
- top-level `generate` and `migrate` aliases;
- `schema print`;
- `plugins list`, `plugins add`, `plugins remove`;
- `completions`.

Eight binary aliases are declared. The CLI reads static `rustauth.toml`, emits
versioned SQL, and currently targets SQLx-backed schema workflows rather than
executing TypeScript configuration or generating Prisma/Drizzle models. Its secret
format is Base64 rather than the upstream CLI's recorded hex output. It adds
validation, dry-run and unsafe-operation guards, and migration deduplication.

Explicit omissions are TypeScript server-module execution, client generation, social
environment discovery, auth-toggle generation, ORM-specific output, and an
`auth-api` generator. Current `init` requires explicit framework and database adapter
choices. Live PostgreSQL/MySQL migration coverage, serialized concurrent migration,
deep init coverage, and live telemetry remain evidence/operational risks.

## Runtime adapter inventory

| Crate | Public contract | Observable differences and risks |
|---|---|---|
| `rustauth-axum` | router nesting/fallback helpers, request/response conversion, proxy controls, base-URL inference controls, body limit, `ConnectInfo` support | native Axum routing instead of JS middleware; 10 MiB body limit; inference disabled unless configured; build-time validation and sanitized 500 responses. Middleware that consumes bodies and missing `ConnectInfo` are integration hazards, not declared parity gaps. |

## Persistence adapter inventory

All database adapters consume the shared logical `DbSchema`; schema semantics and
field transforms are primarily owned above the adapter layer.

| Crate | Supported backend/public surface | Declared differences, gaps, and risks |
|---|---|---|
| `rustauth-sqlx` | SQLite, PostgreSQL, MySQL; `DbAdapter`, schema/migration planner, dedicated atomic rate-limit store | strict drift detection; wildcard escaping; PostgreSQL arrays vs JSON elsewhere; MySQL `datetime(6)`; single-row delete semantics; no implicit list limit. MSSQL/Bun/D1 are unsupported. Direct `with_schema` can bypass higher transforms; live PG/MySQL evidence is thinner than SQLite. |
| `rustauth-diesel` | PostgreSQL and MySQL; shared schema/migration plan | SQLite is deferred; MySQL arrays use JSON; generated UUIDs on MySQL are unsupported. Its `UPSTREAM.md` lacks the explicit differences/gaps/test-evidence structure used elsewhere, making this declared baseline incomplete. |
| `rustauth-tokio-postgres` | single PostgreSQL client, transaction gate, shared schema/migrations | transaction callback returns unit; no nested transactions; caller creates schema; adapter factory/API shape differs from upstream. Live PG evidence and shared-suite coverage remain risks. |
| `rustauth-deadpool-postgres` | PostgreSQL pool-backed adapter, shared schema/migrations | pool integration and no nested transactions; single-row delete and no default list limit; legacy JSONB array handling is manual. Live-service and test depth remain risks. |
| `rustauth-redis` | secondary storage and atomic rate-limit store; native TLS/Rustls options | uses a Rust `secondary:` namespace, zero TTL deletes, SCAN rather than KEYS, Lua rate limiting, CAS/take extensions. Better Auth Redis data is not directly import-compatible; migration is required. |
| `rustauth-fred` | Fred-backed secondary storage and atomic rate-limit store; native TLS/Rustls options | same namespace/TTL/SCAN/Lua/CAS differences; pre-secondary legacy Fred data is not read, and reconnect/cluster behavior is delegated to Fred. Its declared test/example evidence is stale. |

Redis and Fred session payload portability is outside the declared direct-import
contract. Both adapters intentionally extend the upstream-style secondary-store
surface with atomic operations needed by RustAuth's security-sensitive flows.

## Consolidated observable exception register

These are the exceptions the v1.6.24 map must explicitly preserve, change, or retire.

| Area | Observable exception or extension | Current classification |
|---|---|---|
| Core health | `/ok` is plain text rather than JSON | intentional divergence |
| Core account linking | verified-email/trusted-provider gates are stricter | security hardening |
| Errors/input | typed fail-closed errors and strict identifier/origin/secret checks | security hardening/Rust API |
| Plugin One Tap | missing email uses HTTP 400 rather than recorded upstream 200 error | intentional divergence requiring re-evaluation |
| Generic OAuth/social | stricter ID-token/opaque-token/JWKS and SSRF behavior | security hardening |
| OAuth provider | client update uses `POST`, not recorded upstream `PATCH` | known user-visible gap |
| OAuth provider storage | plural snake-case tables; hashed stored tokens | intentional schema/hardening |
| SAML | signed assertions required by default; unavailable crypto fails closed | security hardening |
| SCIM | hashed tokens, owner checks, unlink-on-delete, fail-closed roles, `Me` 501 | intentional differences plus explicit unimplemented endpoint |
| Passkey | generic unknown-credential error, fresh-session mutation, atomic challenges | security hardening |
| Stripe | durable webhook idempotency and anti-spoof metadata checks | intentional extension/hardening |
| CLI | static TOML/SQL model, Base64 secrets, no TS/ORM/client generation | intentional product boundary |
| Actix | response version/extensions and arbitrary request extensions omitted | known adapter gap |
| SQL adapters | supported backend set and single-row delete semantics differ | intentional boundary/adapter semantics |
| Redis/Fred | Rust namespace, zero-TTL delete, atomic extensions, no transparent upstream-data import | intentional extension plus migration requirement |

The following are Rust implementation choices unless their observable consequences
change: the 23-crate split, Tokio task-local context, `webauthn-rs`, `opensaml`,
concrete SQL libraries, typed callbacks, and in-process cache representation.

## Baseline conclusions for the v1.6.24 map

1. Treat the route and schema registration code as the baseline authority when it
   contradicts prose; update the declaration only after the target disposition is
   decided.
2. Track HTTP behavior, defaults, persistent names/types, migrations, cookie/session
   behavior, and CLI effects as user-visible contracts.
3. Track exports, builders, traits, callback shapes, and Cargo features as Rust-public
   compatibility contracts, but do not require TypeScript API-shape mimicry where the
   HTTP contract is preserved.
4. Give every recorded hardening behavior an explicit preserve/change decision.
   Security-sensitive validation should not be relaxed accidentally in pursuit of
   textual parity.
5. Give the known gaps—OAuth provider `POST`/`PATCH`, Actix metadata loss, SCIM
   `Me`, Diesel SQLite, and storage migration boundaries—named owners and tests if
   they remain in the v1.6.24 target.
6. Refresh parity evidence as part of later implementation tickets: generated or
   code-derived route/schema/feature inventories would be more reliable than copied
   counts.
7. Separate unsupported platforms and client packages from server parity so they do
   not appear as accidental gaps.

This report establishes the v1.6.9 starting surface only. It does not decide the
v1.6.24 target, implement parity changes, or alter production behavior.
